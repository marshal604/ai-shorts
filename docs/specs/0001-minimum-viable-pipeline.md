# Spec 0001：最小可用管線（交易類別）

狀態：ready-for-agent
範圍：從一支本機長影片產出短影片的完整四階段管線，僅實作交易分析類別。

## Problem Statement

使用者每天錄製 15 到 30 分鐘的交易分析螢幕錄影，其中真正值得單獨發布的內容通常只有一兩段。手動剪成直式短影片耗時且重複。

現成工具（AlphaCut、Opus Clip 及其開源仿作）全部建立在同一個假設上：畫面裡有人臉、價值在「講得好的話」。這個假設在無人臉的 TradingView 螢幕錄影上完全失效——人臉追蹤無從追起，而語意選段會挑出「聽起來完整」的句子，卻剪掉交易分析真正的價值所在：講的話正對著的那張圖。更糟的是，這些工具的自動裁切會把 K 線圖與價格軸切爛。

使用者也不信任「AI 自動判斷哪裡是重點」——同一支長影片跑兩次得到不同結果，就無法透過調整設定讓產出穩定。

## Solution

一支 CLI 工具，吃一支本機長影片，產出每個區段一支的 1080×1920 短影片，外加對應的標題與描述檔。

定位完全不猜：使用者在錄影當下口頭喊出口令（`這筆進場`、`這筆止盈`、`這筆止損`），系統以字串比對找出錨點，再把取材範圍限縮在錨點附近。找不到錨點的長影片直接不受理。

管線分四個階段，每階段產出一份可讀、可手改、可單獨重跑的 JSON。使用者對哪一段不滿意，就改那一份 JSON 重跑後續階段，不必重跑昂貴的轉錄，也不必重打 LLM。LLM 回應以輸入雜湊為 key 快取到磁碟，所以同一支長影片重跑會得到相同結果。

## User Stories

1. 作為交易者，我想把一支本機長影片丟給一個指令，就拿到可直接上傳的短影片，這樣我不用手動剪片。
2. 作為交易者，我想只提供本機檔案路徑，不必先上傳到任何服務，這樣我的交易紀錄不會外流。
3. 作為交易者，我想在錄影當下用口令標記進場，這樣系統不必猜哪裡是重點。
4. 作為交易者，我想在錄影當下用口令標記結果（止盈／止損），這樣短影片知道這筆交易怎麼收尾。
5. 作為交易者，我不想逐字背台詞，希望我說「那這筆就是進場」也算數，這樣口令不會因為我多講兩個字就失效。
6. 作為交易者，我希望系統忽略「有人想要在這邊進場也是有可能的」這種講解句，這樣講解不會被誤認成事件。
7. 作為交易者，我希望系統忽略「那這筆方向就做錯了」這種帶前綴但非事件的句子，這樣誤報不會產出垃圾短片。
8. 作為交易者，我希望轉錄把「止盈」聽成「只贏」時系統仍然認得，這樣我不必為了語音辨識去改變講話方式。
9. 作為交易者，我希望轉錄吐出簡體「损」時系統仍然認得，這樣繁簡混雜不會讓口令失效。
10. 作為交易者，我想讓一支長影片裡的每個區段各自產出一支短影片，這樣我一次錄影可以發多支片。
11. 作為交易者，我想在渲染之前先看到系統找到哪些錨點與區段，這樣我可以當場發現自己漏喊了口令。
12. 作為交易者，我想在區段重疊時看到明確的錯誤，而不是拿到一支把甲的進場配乙的結果的短片，這樣錯誤不會靜悄悄地混過去。
13. 作為交易者，我想手動修改錨點檔再重跑，這樣漏喊的口令我可以事後補上，不必重錄。
14. 作為交易者，我想手動修改骨架計畫檔再重渲染，這樣我不滿意某一段的選材時可以直接改。
15. 作為交易者，我想在改計畫檔後重跑時不必重跑轉錄，這樣迭代只要幾秒而不是幾分鐘。
16. 作為交易者，我想讓同一支長影片重跑兩次得到相同結果，這樣我調整設定時看到的差異來自設定本身，不是來自隨機性。
17. 作為交易者，我想讓短影片開頭三秒就看到結果畫面，這樣觀眾有理由看下去。
18. 作為交易者，我不想在開頭與結尾聽到同一句話播兩次，這樣短影片不會顯得廉價。
19. 作為交易者，我想讓短影片依「結果鉤子 → 盤面分析 → 進場點位 → 進場 → 持倉 → 結果揭曉」的順序推進，這樣觀眾跟得上我的思路。
20. 作為交易者，我想在持倉過程很長時看到快轉，這樣短影片不會卡在等待。
21. 作為交易者，我想在持倉過程只有 20 秒時讓那個位置直接消失而不是報錯，這樣短打的交易也能成片。
22. 作為交易者，我想讓短影片長度落在 45 到 60 秒，這樣它符合短影音平台的完播習慣。
23. 作為交易者，我想讓 K 線圖在直式畫面裡看得清楚，這樣觀眾能看懂我在講什麼。
24. 作為交易者，我想讓價格軸的數字保持可讀，這樣觀眾知道現在的價位。
25. 作為交易者，我不想在畫面上看到 TradingView 的工具列，這樣短影片不像未經處理的錄影。
26. 作為交易者，我不想讓圖表右側的空白佔掉畫面，這樣有效資訊佔滿版面。
27. 作為交易者，我不想為了工具去調整我的 TradingView 設定，這樣我的錄影流程不受影響。
28. 作為交易者，我想讓裁切框在同一個片段內固定不動，這樣畫面不會抖。
29. 作為交易者，我想讓講解結構的段落看得到左側的歷史 K 線，這樣「這邊碰到 FVG」這種話有畫面對照。
30. 作為交易者，我想讓講進場點位的段落放大右側，這樣進場價與 TP／SL 框看得清楚。
31. 作為交易者，我想要全程燒錄字幕，這樣觀眾靜音也看得懂。
32. 作為交易者，我想要字幕依閱讀單位斷行而不是依語音停頓，這樣字幕不會擠成三行擋住圖表。
33. 作為交易者，我想讓損益數字與價位在字幕裡被強調，這樣最關鍵的資訊最醒目。
34. 作為交易者，我想讓字幕裡的專有名詞正確（FVG 而不是 FBG 或小肥波），這樣短影片不會因為錯字失去可信度。
35. 作為交易者，我想讓字幕與標題避開平台底部 UI 會遮住的區域，這樣資訊不會被擋掉。
36. 作為交易者，我想在每支短影片旁邊拿到標題、描述與 hashtag，這樣我上傳時可以直接複製。
37. 作為交易者，我想讓輸出檔名帶有時間碼與結果，這樣我一眼認得出哪支是哪筆交易。
38. 作為交易者，我想讓所有中間產物集中在一個資料夾，這樣我不會在專案裡到處找檔案。
39. 作為交易者，我想在轉錄前把我的術語表餵給語音辨識，這樣專有名詞從源頭就少錯。
40. 作為交易者，我想讓語音辨識在本機跑，這樣不花 API 費用也不上傳音訊。
41. 作為維護者，我想讓題材知識全部集中在類別定義裡，這樣未來新增類別時引擎不用改。
42. 作為維護者，我想在編譯期就抓到寫壞的類別定義，這樣錯誤不會拖到執行期才爆。
43. 作為維護者，我想讓整條領域邏輯在一個純函式接縫下可測，這樣測試不必啟動 whisper 或 ffmpeg。
44. 作為維護者，我想用真實影片的逐字稿當測試素材，這樣測試涵蓋的是真的會發生的轉錄怪異，不是我想像出來的。
45. 作為維護者，我想讓 LLM 的磁碟快取同時充當測試 fixture，這樣測試不需要 mock 框架也能決定性。

## Implementation Decisions

### 執行環境與形態

TypeScript on Node 20，以 `tsx` 直接執行、無建置步驟；薄的可執行檔包覆型別化的模組。沿用使用者既有的 `youtube-transcription` 專案的技術基底，但兩專案不共用程式碼、不互相相依。外部相依只有 `ffmpeg` 與 `whisper-cli`，皆為既有安裝。

CLI 分四個階段，各自可單獨執行，也可一次跑完：轉錄、定位、規劃、渲染。階段之間以檔案系統上的 JSON 溝通，不以記憶體傳遞。

### 輸出結構

一支長影片對應一個輸出資料夾，內含轉錄產物、錨點產物、計畫產物，以及每個區段一組的短影片檔與 metadata 檔。短影片檔名帶有序號、起始時間碼與結果。錨點與計畫兩份產物是**契約的一部分**，使用者可以手動編輯後重跑下游階段，程式必須容忍手改過的內容（只做結構驗證，不假設是自己寫的）。

### 轉錄

以 `ffmpeg` 抽出 16 kHz 單聲道 WAV，交給本機 `whisper.cpp` 的 `large-v3-turbo` 模型，啟用 Silero VAD、指定語言為中文。類別提供的術語表以 initial prompt 餵入以提升專有名詞準確度。逐字稿保留逐段時間碼。

### 正規化

比對前必須先正規化：繁簡轉換、全形半形統一、英文大小寫統一。這一步是**強制的**，不是選項——實測樣本中真正的簡體字只有兩個，但兩個都落在出場口令上。

正規化後把所有段落串成單一全文，並保留字元位置到時間碼的對照表。**所有比對都在全文上做，再反查時間碼**；不得逐段比對，因為 whisper 的段落邊界是語音停頓，同一句口令會被切開。

### 定位（見 ADR-0001）

事件由**來源準備階段**依語意標記，不做字串比對。該階段本來就要讀完整份逐字稿來校正錯字，讓它順便標記事件的邊際成本是零——原本否決「模型做偵測」的唯一理由（整份餵進去太貴）因此不成立。

好處是講者不必說出固定字眼：「這筆進場」「這邊就進場」「我現在進了」都算數。實測十三分鐘樣本裡，兩個進場宣告根本不含任何固定前綴，字串比對再怎麼加變體也抓不到。

曾經有一層前綴字串比對作為交叉檢查，實測真陽性 0、偽陽性 1，已移除。

### 類別（見 ADR-0004）

題材知識全部收進類別，引擎只操作抽象概念，不認得「進場」或「止盈」。類別以 TypeScript 模組撰寫，不用 JSON——型別檢查能在編譯期擋掉寫壞的定義，而這是個人工具，沒有非工程師編輯類別的需求。

型別形狀（已實作，`Locator` 為可辨識聯集，v1 只有一個成員）：

```ts
interface Category {
  name: string
  vocabulary: EventVocabulary
  skeleton: Position[]
  glossary: Record<string, string>
  duration: { target: number; min: number; max: number }
}

interface EventVocabulary {
  events: Array<{
    id: string
    role: 'open' | 'close'
    description: string   // 給標記階段讀的自然語言，不是比對字串
    outcome?: string
  }>
}

interface Position {
  id: string
  cardBrief: string       // 這個位置的文案要傳達什麼
  // 只規定「可以從哪裡取材」，不規定切點 —— 實際取哪一段由規劃器依內容決定
  source: { anchor: 'open' | 'close'; direction: 'before' | 'after' | 'around'; reach: number }
  collapsible: boolean
}
```

骨架位置引用**錨點的相對窗口**，不引用題材概念——引擎不知道 `close` 代表止盈還是止損。位置必須可塌縮：素材不足時位置消失、骨架縮短，不報錯。

### 區段配對

假設同一支長影片中的區段互不重疊（一次只持有一筆）。偵測到重疊時**直接報錯中止，不做任何猜測**——猜錯會產出一支看起來完全正常、但把甲的進場配乙的結果的短片，使用者不會發現。

### 取材窗口

窗口自錨點向外展開至類別指定的上限，但碰到鄰近區段的錨點就截斷，因此各區段的取材範圍互不重疊。只有窗口內的逐字稿會餵給 LLM；區段中段（持倉）只提供畫面，其逐字稿一律丟棄。

### 規劃

單次 LLM 呼叫（Claude Sonnet 5），輸入為窗口內含時間碼的逐字稿與類別的骨架定義，輸出為每個骨架位置的起訖時間碼、字卡文案與標題描述。以 tool use 強制輸出符合 schema。

**回應以輸入雜湊為 key 快取到磁碟**，不倚賴 API 的 temperature 保證。這同時滿足三件事：重跑不花錢、結果可重現、以及改了 prompt 才失效重算。

單次呼叫而非多階段，因為各位置要互相協調總長度，拆開反而難收斂。

### 構圖（見 ADR-0003）

裁切框由像素分析自動決定，不用固定矩形、也不要求使用者調整錄影設定。作法：取灰階原始幀，以全幀眾數為背景色，逐欄／逐列統計偏離背景超過門檻的像素比例，找出內容邊界。實測能乾淨切出頂部工具列、左側工具列、內容右緣、死留白、價格軸五個區塊。

死留白寬度會隨時間變動，因此以水平堆疊把價格軸接到內容右緣、把留白整塊剪掉。這是刻意的視覺造假，換取約三成的有效畫面。裁切右界需留餘裕，否則最下方的價格標籤會貼邊被切。

**裁切框每個片段算一次，片段內固定不動**——逐幀重算會讓畫面持續抖動。

### 版面

輸出 1080×1920，分三帶：上方標題帶、中段圖表帶、下方字幕帶；底部保留給平台 UI，不放任何內容。圖表帶有兩種填法：全幅（裁掉 UI chrome 後整幅置中，保留左側歷史脈絡）與放大（內容感知裁切後幾乎填滿）。骨架的每個位置指定用哪一種。

### 文字圖層（見 ADR-0002）

開發機的 ffmpeg 未編入 freetype 與 libass，`drawtext`／`subtitles`／`ass` 皆不可用。文字改由 Satori（JSX 版面轉 SVG）加 resvg（SVG 轉 PNG）在 Node 內產生透明圖層，再由 ffmpeg 疊上。ffmpeg 只負責解碼、裁切、縮放、變速、堆疊、拼接、編碼。

字幕依閱讀單位重新斷行，不沿用轉錄的段落邊界；損益數字與價位加粗變色。專有名詞經類別的術語表校正後才進字幕。

### 渲染

純 ffmpeg。持倉位置以變速濾鏡快轉並靜音。片段依骨架順序拼接。文字圖層組成單一軌後一次疊上，避免濾鏡圖爆炸。

## Testing Decisions

**好的測試只驗外部行為。** 這裡的「外部行為」是：給定一份逐字稿與一個類別，產出的計畫是什麼；給定一幀畫面，算出的裁切框是什麼。不驗中間步驟怎麼分工、不驗函式如何拆分、不驗資料在模組間怎麼傳。重構管線內部不應該讓任何測試變紅。

**沒有既有測試可以參照。** 本專案是全新的；相鄰的 `youtube-transcription` 專案也只有型別檢查、沒有測試。因此本 spec 同時是這個專案的測試風格起點。

### 接縫一（主要）：逐字稿加類別產出計畫

一個純函式，涵蓋正規化、分層定位、區段配對、取材窗口、骨架填充的全部領域邏輯。這是唯一能出錯的地方，也是唯一需要密集測試的地方。

素材用**三支真實影片的逐字稿**，不用手寫假資料——真實資料裡的轉錄怪異（口令中插入「就是」、簡體字、專有名詞誤轉、前綴誤報）是想像不出來的。

要驗的行為：前綴的每一次出現都被找到（含跨段落被切開者）；含事件詞但無前綴的講解句不成為候選；繁簡混雜不影響偵測；分類器判定為非錨點的候選被濾掉；區段重疊時拋錯；取材窗口碰到鄰近錨點時截斷；素材不足時骨架位置塌縮而非報錯；總長落在類別指定的範圍。分類器以預先備妥的快取內容驅動，因此整個接縫是決定性的。

**LLM 以磁碟快取當 fixture。** 快取本來就在設計裡（可重現性需求），測試只需預先備妥快取內容，這個接縫就完全決定性——不需要 mock 框架，也不必為測試新增任何接縫。

### 接縫二：畫面幀產出裁切框

一個純函式，輸入灰階像素緩衝與尺寸，輸出矩形。素材用兩張從真實影片抽出的灰階幀。要驗的行為：內容右緣落在預期比例區間；價格軸被保留；死留白被排除；UI chrome 被排除。

這個接縫與接縫一零共用邏輯（一個吃文字、一個吃像素），刻意不合併——硬併只會生出一個假抽象。

### 接縫三：端到端 golden（非單元測試）

完整 CLI 吃十分鐘樣本，斷言產出一支短影片、時長落在類別範圍內、錨點產物含一個區段且結果為止損。因為要跑 whisper 與影片編碼，執行時間以分鐘計，手動觸發，不進監看模式。

### 刻意不設接縫

whisper 呼叫（第三方 process）、ffmpeg 組裝（由 golden 涵蓋）、Satori 版面（由產出的 PNG 目視檢查）。

## Out of Scope

- **前綴以外的定位訊號**（弱訊號候選、指示代詞密度）：`Locator` 預留分支，v1 不實作。
- **部分止盈**：類別保留該事件，但從未在任何樣本中出現，行為未驗證。
- **交易以外的類別**：介面通用，實作只有交易一個。
- **口令以外的定位策略**：`Locator` 是可辨識聯集，但只有口令一個成員。
- **自動上傳**：產出停在本機檔案與 metadata 文字。
- **跨影片整合**：一支長影片獨立處理，不做跨影片素材庫。
- **從網址下載長影片**：只吃本機檔案。
- **AI 旁白、AI 生成圖卡、背景音樂**。
- **滑鼠游標追蹤裁切**：游標位置確實可用來對準裁切中心，但排在自動裁切實際跑歪之後。
- **沒有錨點的長影片**：不受理，不做降級處理。

## Further Notes

### 未驗證的假設（動工後最可能翻車）

1. **多區段配對完全沒測過**。三支樣本各只有一筆交易，開啟錨點出現兩次以上的行為是紙上推演。
2. **部分止盈的口令從未被說出過**，轉錄結果未知。
3. **Satori 加 resvg 的中文字型與斷行未實測**。
4. **六個骨架位置塞進 45 到 60 秒未真的排過**。十分鐘樣本顯示持倉常常只有 20 秒、持倉位置會頻繁塌縮，這代表大部分片長要由盤面分析與進場點位兩段扛，那兩段的壓縮品質比原先估計的更關鍵。
5. **使用者的口令習慣仍在建立中**。三支樣本中，第二支完全沒喊結束口令，第三支的開啟口令是「那這筆就是進場」而非約定的形式。這是分層定位存在的理由。

### 已驗證的事實

- 本機 whisper 在使用者聲音上的繁中轉錄品質足夠。
- 前綴在 145 支同題材影片、231,715 個逐字稿段落中僅出現一次；在三支自錄樣本中召回率百分之百、精確率三分之二。
- 前綴在十分鐘樣本上找到三個候選，涵蓋全部兩個真事件；第三個（「這筆方向就做錯了」）是分類器要濾掉的誤報。
- 內容感知裁切的視覺結果明顯優於固定矩形與整幅縮放。
- 開發機的 ffmpeg 具備所有非文字類濾鏡，且缺少全部文字類濾鏡。
